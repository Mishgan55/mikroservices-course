# ADR-002. Ограниченные контексты и контейнерная архитектура

- **Дата:** 2026-08-24
- **Статус:** Предложено
- **Связан с:** [ADR-001](../Task1/ADR-001-context.md)

---

## 1. Контекст

ADR-001 зафиксировал выбор верхнеуровневой архитектуры (Вариант 1 — автономная
ферма, тонкий центр). Теперь требуется разрезать систему на ограниченные
контексты и спроектировать состав контейнеров для обоих вариантов.

## 2. Принцип выделения контекстов

Границы проводятся по **единству языка**, а не по технологии реализации.
Внутри одного контекста термин имеет ровно одно значение.

Пример. Слово «животное» в разных контекстах означает разное:

| Контекст | Что такое «животное» |
|---|---|
| Здоровье животных | Пациент: состояние, диагноз, назначения |
| Поголовье | Единица учёта: загон, приплод, падёж, перемещение |
| Видеоаналитика | Трек: bounding box, идентификатор на кадре, уверенность модели |

Попытка построить единую модель «Животное» на все случаи даёт раздутую сущность,
за которую конкурируют несколько команд.

**Проверочный критерий границы:** если заменить технологию источника данных
(например, камеры на RFID-метки), контекст «Поголовье» сохранится без изменений,
а контекст «Видеопоток» исчезнет. Значит, это разные контексты, и склеивать их
нельзя — иначе смена источника данных потребует переписывания учёта, что
нарушает НФТ о расширяемости без изменения существующего кода.

## 3. Карта ограниченных контекстов

### Ядро домена (уникальная логика, разрабатываем сами)

| Контекст | Ответственность | Ключевые термины |
|---|---|---|
| **Видеоаналитика и детекция** | Исполнение ML-моделей на видеопотоке, генерация технических событий детекции | трек, детекция, уверенность, кадр |
| **Здоровье и благополучие животных** | Интерпретация событий в доменные инциденты, карточка животного, диагнозы | инцидент, состояние, диагноз, назначение |
| **Поголовье** | Учёт голов, приплод, падёж, перемещения между загонами | голова, загон, приплод, падёж |
| **Кормление и поение** | Расписания, команды оборудованию, учёт расхода, прогноз остатков корма | рацион, доза, кормление, остаток |

### Поддерживающие контексты

| Контекст | Ответственность | Почему отдельный |
|---|---|---|
| **Водоподготовка** | Мониторинг фильтров и качества воды | Своё оборудование, свой словарь, меняется независимо |
| **Видеопоток и камеры** | Подключение камер, RTSP, транскодирование, адаптеры вендоров | Инфраструктурная задача, изолирует вендорские различия |
| **Управление устройствами и парком агентов** | Реестр ферм, камер, кормушек, агентов. Адаптеры протоколов, OTA-обновления, канареечный раскат | Без него невыполнимо ФТ «без ограничения количества агентов» |
| **Оповещения** | Каналы (сирена, SMS, push), шаблоны, эскалация, подавление дублей, подтверждение получения | Сквозная способность: нужна нескольким контекстам и меняется по своим причинам. Словарь не содержит доменных терминов животноводства |
| **Синхронизация агент ↔ центр** | Очередь исходящих событий, докачка после обрыва, разрешение конфликтов, идемпотентность | Прямо следует из ФТ о допустимой задержке 10 минут |

### Общие контексты (берём готовое, не разрабатываем)

| Контекст | Решение | Обоснование |
|---|---|---|
| **Доступ и роли** | Keycloak (OAuth2/OIDC) | Написание своего IdP — типовая ошибка. Готовое решение закрывает ФТ о «современных способах аутентификации» |
| **Наблюдаемость и метрики** | Prometheus + Grafana, OpenTelemetry | Стандарт индустрии. Формат exposition закрывает ФТ о передаче метрик в другие системы и о добавлении собственных |
| **API для приложений** | API Gateway / BFF | Единая точка входа для мобильного и веб-приложения |

**Вывод для планирования бюджета:** экономить следует на общих контекстах
(готовые решения), вкладываться — в ядро домена.

## 4. Диаграммы контейнеров

- Вариант 1 (основной): [`c2-variant1.puml`](./c2-variant1.puml)
- Вариант 2 (альтернативный): [`c2-variant2.puml`](./c2-variant2.puml)

### 4.1. Размещение контекстов по вариантам

| Контекст | Вариант 1 | Вариант 2 |
|---|---|---|
| Видеопоток и камеры | Агент | Шлюз (только транскодирование) |
| Видеоаналитика и детекция | **Агент (GPU)** | **Центр (GPU-ферма)** |
| Здоровье и благополучие | **Агент** | **Центр** |
| Кормление и поение | **Агент** | **Центр**, команды через шлюз |
| Водоподготовка | Агент | Центр |
| Оповещения | **Агент** | **Центр** |
| Поголовье: подсчёт | Агент | Центр |
| Поголовье: реестр и история | Центр | Центр |
| Управление парком | Центр | Центр (проще: шлюзы почти не обновляются) |
| Синхронизация | Агент + Центр | Шлюз (буфер) + Центр |
| Доступ и роли | Центр | Центр |
| Наблюдаемость | Агент + Центр | Центр |
| API для приложений | Центр + локальный API на агенте | Только центр |

### 4.2. Критический путь оповещения

Вариант 1 — целиком внутри фермы, границу не пересекает:

    Камеры -> Приём видеопотока -> Инференс -> Локальная шина
          -> Благополучие -> Оповещения -> Сирена / SMS

Вариант 2 — дважды пересекает WAN:

    Камеры -> Транскодирование -> [ИНТЕРНЕТ] -> Шлюз приёма -> Инференс
          -> Kafka -> Благополучие -> Оповещения -> [ИНТЕРНЕТ] -> Шлюз -> Сирена

Оценочный бюджет задержки (порядок величин):

| Шаг | Вариант 1 | Вариант 2 |
|---|---|---|
| Захват и декодирование | ~100 мс | ~100 мс |
| Транскодирование для передачи | — | ~200 мс |
| Передача в центр | — | 0,5–3 с (WiFi/4G, нестабильно) |
| Инференс | ~50–150 мс | ~50–150 мс |
| Логика инцидента | ~50 мс | ~50 мс |
| Обратный канал до сирены | ~10 мс | 0,5–3 с |
| **Итого** | **~0,3–0,5 с** | **~1,5–7 с, нестабильно** |

Вариант 1 укладывается в НФТ с запасом более чем на порядок. Вариант 2 при
благоприятном канале укладывается, при деградации канала — нет, и гарантировать
5 секунд не может в принципе.

## 5. Интеграции и обоснование технологий

### 5.1. Локальная шина агента: RabbitMQ + MQTT

Преимущества:

- Поддержка MQTT «из коробки» — тот же брокер обслуживает и сервисы, и устройства.
  Не требуется отдельный мост MQTT в шину.
- Нетребовательность к ресурсам, что критично для промышленного мини-ПК на ферме.
- Распространённая технология, низкий порог входа для команды.
- Поддаётся кластеризации, если на крупной ферме потребуется резервирование.

Ограничение: при росте нагрузки выше нескольких десятков тысяч сообщений в
секунду RabbitMQ уступает Kafka. На уровне одной фермы этот порог недостижим,
поэтому ограничение неактуально. Если ферма вырастет до сотен камер, потребуется
пересмотр.

### 5.2. Шина центра: Apache Kafka

Преимущества:

- Рассчитана на поток со всех ферм одновременно (сотни тысяч сообщений в секунду).
- Хранение лога с возможностью переигрывания — необходимо для переобучения моделей
  и разбора инцидентов задним числом.
- Уже используется в компании: не нужно вводить новую технологию и обучать эксплуатацию.
- Экосистема Kafka Connect закрывает выгрузку в Data Lake, DWH и BI без своего кода.

Ограничение: тяжеловесна, требует отдельной команды эксплуатации. На ферме неприменима.

Принцип: одна и та же задача на разных масштабах решается разными технологиями.
Единообразие ради единообразия отвергнуто как аргумент.

### 5.3. Остальные интеграции

| Что с чем | Технология | Почему именно так |
|---|---|---|
| Видеопоток внутри агента | Shared memory / gRPC | Копирование кадров через сеть съело бы бюджет задержки. Нужен нулевой оверхед |
| Камеры в агент | RTSP / ONVIF | Отраслевой стандарт, поддерживается всеми крупными вендорами. Изолируется адаптером |
| Агент к оборудованию | Modbus TCP и проприетарные протоколы через Адаптер оборудования | Вендорские различия прячутся за одним внутренним интерфейсом. Добавление вендора = новый адаптер без правки бизнес-логики (закрывает НФТ о расширяемости) |
| Агент в центр | HTTPS + mTLS, пакетная отправка, transactional outbox | Переживает длительные обрывы: клиент Kafka требует стабильного соединения и плохо ведёт себя при многочасовом отсутствии связи. Outbox гарантирует, что ни одно событие не потеряется |
| Резервный канал связи | 4G/LTE с автопереключением, GSM для SMS | ФТ требует альтернативу нестабильному WiFi. SMS проходит там, где не проходит интернет |
| Синхронные запросы UI | REST через API Gateway | Простота, кэширование, стандартная авторизация по JWT |
| Реальное время в UI | WebSocket | Тревоги должны появляться без опроса сервера |
| Аутентификация | OAuth2 / OIDC (Keycloak), JWT | Закрывает ФТ о современных способах. Роли централизованы, агент валидирует токены локально по кэшированным ключам — работает без интернета |
| Метрики | OpenTelemetry + Prometheus exposition | Стандартный формат закрывает ФТ о передаче метрик в другие системы. Собственные метрики добавляются как плагины без правки кода сервисов |
| Интеграция с ERP | REST API к 1С:Агро | Существующий контракт компании, уже используется в as-is |
| Выгрузка в аналитику | Kafka Connect в MinIO и ClickHouse | Переиспользуется существующий конвейер компании |

## 6. Компромиссы и риски

### 6.1. Компромиссы варианта 1

| Компромисс | Обоснование | Как смягчаем |
|---|---|---|
| Согласованность между агентом и центром только конечная (eventual) | Прямо разрешено ФТ: задержка до 10 минут | Идемпотентные обработчики, версионирование записей, правило «агент — источник истины по своей ферме» |
| Дублирование логики: благополучие и подсчёт есть и на агенте, и в центре | Иначе не выполнить автономность | Общие библиотеки домена, единая схема событий, контрактные тесты |
| Буфер на ферме ограничен объёмом диска | Физическое ограничение | Приоритизация: инциденты и метаданные сохраняются всегда, видеофрагменты вытесняются первыми по кольцу |
| Дрейф версий ML-моделей между фермами | Следствие офлайн-работы | Версия модели пишется в метаданные каждого события: при разборе видно, чем он получен |

### 6.2. Риски варианта 1

| Риск | Влияние | Митигация |
|---|---|---|
| Отказ ферменного сервера (SPOF) | Ферма теряет мониторинг | Сторожевой модуль на независимом контроллере даёт аварийную сирену и SMS. ЗИП на складе, регламент замены |
| Высокий CAPEX при масштабировании | Бюджет проекта | Поэтапный раскат, пересмотр конфигурации GPU после MVP |
| Сложность обновления парка агентов | Дрейф версий, рассинхронизация | Fleet management: OTA, канареечный раскат, автоматический откат по метрикам |
| Ложные срабатывания моделей (тени, похожие особи) | Усталость оператора от тревог | Пороги и подавление дублей в сервисе благополучия, обратная связь оператора для дообучения. Для MVP признано некритичным |

### 6.3. Риски варианта 2

| Риск | Влияние | Митигация |
|---|---|---|
| Невыполнение НФТ 5 секунд при деградации канала | Нарушение ключевого требования | Митигации нет: ограничение архитектурное |
| Потеря мониторинга при обрыве связи | Нарушение ФТ об офлайн-работе | Аварийный режим на примитивных правилах, видеоаналитика недоступна |
| Стоимость трафика: непрерывное видео со 150 ферм | OPEX | Транскодирование в H.265, передача по событию вместо непрерывной. Снижает качество детекции |
| Единая точка отказа — центр | Отказ центра останавливает ВСЕ фермы | Кластеризация и георезервирование центра, что удорожает решение и частично съедает его ценовое преимущество |
